# 音楽聴取と場所の関係を可視化する地図SNS「Music Walk Map」の開発

2026年度 卒業論文  

## 構想発表時点の概要

2025年度のゼミ論では、Spotifyの再生履歴に位置情報・気分・天気を付与し、個人の音楽体験を地図上で振り返るWebアプリケーション「音楽散歩地図」を開発した。

卒業論文ではこのシステムを発展させ、単なる個人用の音楽記録アプリではなく、複数のユーザーが位置と音楽を記録・共有できる地図SNS「Music Walk Map」を開発する。

本研究では、日常生活圏において聴かれる音楽が、駅、公園、大学、商業地、住宅地などの場所カテゴリによってどのように異なるのかを明らかにすることを目指す。

そのために、ユーザーが自発的に現在の曲と場所を投稿する「Quick Spot」と、移動中の位置ログとLast.fmの視聴履歴を時刻によって結合する「Recorded Spot」という2種類の記録方式を実装する。

# 1. Introduction

## 1.1 背景

音楽は、人の気分や記憶だけでなく、その音楽を聴いた場所や移動体験とも結びついていると考えられる。

しかし、Spotify、Apple Music、Last.fmなどの一般的な音楽サービスでは、再生履歴は主に曲名と再生時刻の一覧として表示される。そのため、「どこでその曲を聴いたのか」「どのような移動中に聴いたのか」といった空間的な文脈は残りにくい。

一方、位置情報を利用する地図サービスやSNSでは、ユーザーが場所に関する情報を自発的に投稿することで、地理情報が蓄積されていく。このようなユーザー参加型の地理情報は、VGI（Volunteered Geographic Information）や参加型センシングの考え方と関係している。

そこで本研究では、音楽視聴履歴と位置情報を組み合わせ、音楽と場所の関係を記録・共有・分析できる地図SNSを開発する。

## 1.2 2025年度ゼミ論

2025年度のゼミ論では、以下の機能を持つ「音楽散歩地図」のプロトタイプを開発した。

- Spotify OAuthによるユーザー認証
- Spotify APIからの再生履歴取得
- 再生中の曲の15秒間隔での監視
- Geolocation APIによる現在地取得
- OpenWeatherMap APIによる天気取得
- moodの手動登録
- Supabaseへの音楽・位置・天気情報の保存
- MapLibreによる地図上のマーカー表示
- mood、天気、時間帯による簡易集計

ゼミ論版は、個人の音楽体験を地図上で振り返ることを主な目的としていた。

ゼミ論では、再生中の曲を検出した時点の現在地を、その曲の再生場所として保存していた。

しかし、曲の再生開始時刻と位置を取得した時刻には差が生じる。また、1曲につき1地点のみを保存するため、移動中の経路や曲を聴いていた範囲を記録できなかった。

卒論版では、位置情報と音楽視聴履歴をそれぞれ独立した時系列データとして保存し、後から時刻を用いて結合する方式へ変更する。

## 1.4 研究目的

本研究の目的は、位置情報と音楽視聴履歴を組み合わせた地図SNS「Music Walk Map」を開発し、日常生活圏における場所と音楽聴取の関係を可視化・分析することである。

## 1.5 リサーチクエスチョン

### 主たる問い

> 日常生活圏における音楽聴取パターンは、駅、公園、大学、商業地、住宅地などの場所カテゴリによってどのように異なるのか。

### 補助的な問い

- ユーザーによる能動的な投稿と、位置・音楽ログから生成される記録には、どのような違いが生じるか。
- 音楽と場所を組み合わせた地図表示は、ユーザーが自身の移動や音楽体験を振り返る上で有効か。
- 複数ユーザーの音楽記録を地図上で共有することで、場所に対する新しい発見を生み出せるか。

# 2. Method

## 2.1 システム概要

Music Walk Mapは、音楽視聴履歴、位置情報、ユーザー投稿を組み合わせたWebアプリケーションとして開発する。

想定する主要技術は以下のとおりである。

- Next.js
- React
- TypeScript
- Last.fm API
- MusicBrainz API
- Geolocation API
- Supabase
- PostgreSQL
- MapLibre GL JS
- OpenStreetMap

開発にはCodexなどのLLMを活用する。ただし、生成されたコードは技術検証、自動テスト、コードレビューを行った上で採用する。

## 2.2 音楽データの取得

卒論版では、音楽視聴履歴の主要な取得元としてLast.fmを利用する。

SpotifyやApple Musicなどで再生された音楽をLast.fmへScrobbleし、Last.fm APIの `user.getRecentTracks` を通じて視聴履歴を取得する。

Last.fmから取得されるデータは、次の2種類に分けて扱う。

- `nowplaying=true`を持つ再生中の曲
- 再生開始時刻を持つ確定Scrobble

再生中の曲はQuick Spotの投稿候補など、リアルタイム表示に使用する。

Recorded Spotや研究用データには、再生開始時刻が確定したScrobbleを使用する。

MusicBrainzは、曲の識別情報、楽曲時間、タグなどのメタデータを補完するために利用する予定である。

## 2.3 Quick Spot

Quick Spotは、ユーザーが現在聴いている曲と現在地を自発的に投稿する機能である。

想定する処理は以下のとおりである。

1. Last.fmから現在再生中の曲を取得する。
2. 投稿ボタンを押した時点の現在地を取得する。
3. ユーザーが曲と公開場所を確認する。
4. 地図上へSpotとして投稿する。

Quick Spotは、VGIにおける能動的な情報提供に近い記録方式として位置付ける。

## 2.4 Recorded Spot

Recorded Spotは、記録セッション中に取得した位置ログと、Last.fmの確定Scrobbleを時刻によって結合して生成する。

想定する処理は以下のとおりである。

1. ユーザーが記録セッションを開始する。
2. Geolocation APIで位置情報を継続して記録する。
3. セッション終了後、同じ時間帯のLast.fm Scrobbleを取得する。
4. 曲の再生区間を推定する。
5. 曲区間に含まれる位置サンプルを抽出する。
6. 曲区間の中間時刻に最も近い実位置を代表地点にする。
7. ユーザーが公開する曲と場所を確認する。
8. Recorded Spotとして投稿する。

位置情報と音楽履歴は、取得時点では独立したデータとして保存する。

これにより、曲を検出した時点の位置を再生場所として直接保存していたゼミ論版よりも、時刻的な整合性を高めることを目指す。

## 2.5 Journey

Journeyは、1回の記録セッションで得られた移動経路と複数の曲をまとめて公開する機能である。

Recorded Spotと同じ位置ログ・音楽視聴履歴を利用するが、単一の地点ではなく、セッション全体の移動経路と音楽の変化を表現する。

JourneyはRecorded Spot完成後の拡張機能とし、卒論の最低限の完成条件には含めない可能性がある。

## 2.6 時系列結合アルゴリズム

Last.fmの確定Scrobbleが持つ再生開始時刻を、曲区間の開始時刻として利用する。

曲の終了時刻は、以下を組み合わせて推定する。

- 次の曲の再生開始時刻
- MusicBrainzなどから得られる楽曲時間
- 楽曲時間が取得できない場合の暫定時間

曲区間内に複数の位置サンプルが存在する場合は、区間の中間時刻に最も近い位置サンプルを代表地点として選択する。

位置サンプルは緯度・経度の平均値ではなく、実際に取得された座標を使用する。

曲区間は、開始時刻を含み、終了時刻を含まない半開区間として扱う予定である。

```text
[startedAt, estimatedEndedAt)
```

結合結果は、位置データの状態に応じて以下に分類する。

| 状態 | 内容 |
| --- | --- |
| `matched` | 曲区間内に位置サンプルが存在する |
| `partial` | 曲区間外だが、許容時間内に位置サンプルが存在する |
| `unmatched` | 対応可能な位置サンプルが存在しない |
| `pending` | Last.fmの確定Scrobbleを待っている |

## 2.7 データベース設計

Supabase上では、音楽、位置、SNS投稿を単一テーブルにまとめず、役割ごとに分離する予定である。

主要なテーブル候補は以下のとおりである。

- `profiles`
- `music_accounts`
- `tracks`
- `track_external_ids`
- `track_tags`
- `recording_sessions`
- `location_samples`
- `listening_events`
- `posts`
- `post_tracks`
- `post_exact_locations`
- `post_locations`
- `places`
- `likes`
- `research_consents`

Last.fmの同一Scrobbleを重複保存しないため、ユーザー、音楽サービス、再生開始時刻、アーティスト名、曲名から安定した外部イベントキーを生成する予定である。

## 2.8 プライバシー

位置情報は個人の生活圏や行動を推測できる情報であるため、正確な位置と公開用の位置を分離する。

- 正確な位置情報は非公開データとして保存する。
- 公開時には座標をぼかす、または「〇〇駅付近」などの場所表現へ変換する。
- ユーザーが投稿前に公開内容を確認できるようにする。
- SupabaseのRow Level Securityを利用し、ユーザーが自身の非公開データのみを操作できるようにする。
- 研究利用を行う場合は、研究同意とデータ利用範囲を明示する。

## 2.9 分析方法

取得した音楽記録に、OpenStreetMapなどの地理データを用いて場所カテゴリを付与する予定である。

想定するカテゴリは以下のとおりである。

- 駅・公共交通施設
- 大学・学校
- 公園・緑地
- 商業地
- 住宅地
- 道路・歩道
- その他の公共空間

場所カテゴリごとに、以下の傾向を比較する。

- 聴かれた曲数
- アーティスト
- 音楽タグ・ジャンル
- 再生時間帯
- Quick SpotとRecorded Spotの割合
- 必要に応じてmoodや天気などの補助変数

## 3.2 Last.fm取得検証

検証用ページ `/dev/lastfm-test` を実装した。

このページでは、Last.fm APIを15秒間隔で取得し、以下を記録できる。

- API取得時刻
- 現在再生中の曲
- 確定Scrobble
- 再生開始時刻
- ページの表示状態
- APIエラー
- JSON・CSV形式の検証ログ

通常再生、短時間でのスキップ、一定時間再生後のスキップ、同じ曲の連続再生、一時停止と再開について検証を行い、Last.fmを卒論版の音楽履歴取得元として利用できる見通しを得た。

## 3.3 位置情報取得検証

検証用ページ `/dev/location-test` を実装した。

このページでは、Geolocation APIの `watchPosition()` を利用し、以下を記録できる。

- 緯度・経度
- 測位時刻
- GPS精度
- 速度
- 方角
- 高度
- 取得間隔
- ページの表示状態
- JSON・CSV形式のログ

ただし、スマートフォンからLAN内のHTTP開発サーバへアクセスした場合、ブラウザのセキュリティ制約によって位置情報を取得できなかった。

Cloudflare TunnelによるHTTPS化も試みたが、ネットワーク環境に依存する問題が発生したため、スマートフォン実機での継続取得検証は一時保留している。

## 3.4 時系列結合検証

検証用ページ `/dev/timeline-join-test` を実装した。

実際のGPSログを待たずに、ダミー位置ログとLast.fmの確定Scrobbleを時刻で結合する純粋関数を作成した。

```ts
joinScrobblesWithLocations(
  scrobbles,
  locationSamples,
  config,
)
```

結合ロジックはReactやブラウザAPIから分離されており、将来、入力を実際のGPSログやSupabaseのデータへ差し替えられる。

現在までに以下のケースを検証している。

- 正常に曲と位置が結合できるケース
- 曲区間内の位置が不足するケース
- 対応する位置が存在しないケース
- 同じ曲を連続再生するケース
- 入力データの順番が乱れているケース
- 曲の長さが不明なケース
- 曲間に長い空白があるケース
- UTC上で日付をまたぐケース

# 4. Discussion

## 4.1 現時点で得られたこと

Last.fmの確定Scrobbleが持つ再生開始時刻と、独立して記録した位置情報を時刻で結合する方式は、Recorded Spotの基礎として利用できる見通しが得られた。

ゼミ論版では、再生中の曲を検出した時点で現在地を1回取得していた。そのため、再生開始地点ではなく、検出時点の位置が保存される可能性があった。

卒論版では、音楽と位置を独立した時系列として保持することで、曲区間に対応する位置を後から選択できる。

また、結合結果へ `matched`、`partial`、`unmatched`などの状態を残すことで、研究分析時に信頼度の低いデータを識別できる。

## 4.2 現在の課題

現在の主な課題は以下のとおりである。

- スマートフォンのHTTPS環境で連続位置取得を検証できていない。
- モバイルブラウザのバックグラウンド時や画面ロック時の挙動が未確認である。
- 曲区間の境界時刻にある位置サンプルの扱いを追加検証する必要がある。
- Last.fmの同一Scrobbleを安定して識別する外部イベントキーが必要である。
- 不正な日時や座標が入力された場合のバリデーションが必要である。
- MusicBrainzから楽曲時間やタグを安定して取得できるか検証が必要である。
- 正確な位置と公開位置を分離したデータベースとRLSが未実装である。
- 研究で収集するデータ量、対象者、期間、同意方法を確定する必要がある。
- 場所カテゴリをどの範囲・粒度で分類するか決める必要がある。

## 4.3 本研究の意義

本研究は、音楽視聴履歴を単なる時系列データとして扱うのではなく、人の移動や場所と結びついた地理情報として扱う点に特徴がある。

また、ユーザーが意識的に投稿するQuick Spotと、センサーデータと音楽履歴から生成されるRecorded Spotを同一システム内で扱うことで、能動的な情報提供と参加型センシングの違いを比較できる可能性がある。

最終的には、個人の振り返りだけでなく、「この場所ではどのような音楽が聴かれているのか」を複数ユーザーの記録から発見できる地図の構築を目指す。

## 5.3 次の作業

構想発表後は、時系列結合ロジックに残っている以下の3点を修正する。

1. 曲区間を半開区間 `[start, end)` とし、境界位置の二重所属を防止する。
2. Last.fmの同一Scrobbleを再取得後も識別できる、安定した外部イベントキーを生成する。
3. 不正な時刻、曲時間、座標、同一開始時刻などの入力検証を追加する。

修正と自動テストが完了した後、GitHubへのpushとSupabaseの実装へ進む。
