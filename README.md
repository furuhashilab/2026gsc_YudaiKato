# 移動と音楽聴取の関係を可視化する地図アプリ「Music Walk Map」の開発

2026年度 卒業論文  

## 構想発表時点の概要

2025年度のゼミ論では、Spotifyの再生履歴に位置情報・気分・天気を付与し、個人の音楽体験を地図上で振り返るWebアプリケーション「音楽散歩地図」を開発した。

卒業論文ではこのシステムを発展させ、音楽の再生履歴と連続的な位置情報を組み合わせることで、**移動中に場所や移動状況が変化する過程と、聴かれる音楽の変化との関係**を記録・可視化・分析する「Music Walk Map」を開発する。

本研究では、1回の記録セッションから得られる移動経路と複数の楽曲の流れを **Journey** と呼び、研究・可視化の基本単位として扱う。

一方、Journeyほど長時間の記録を行わなくても参加できるように、1曲と1地点を組み合わせた **Spot** も用意する。Spotは、その場で現在の曲と現在地から作成する方法と、Journeyの中から1曲を切り出して作成する方法の2通りを想定する。

本研究における基本構造は、以下のとおりである。

```text
Recording Session
位置ログ＋Last.fmの再生履歴
        ↓
Journey
1回の移動と音楽の流れを表す研究・可視化単位
        ↓
Spot
Journey内の1曲を代表地点と結びつけた比較・共有単位
```

また、Journeyを記録しない場合でも、現在再生中の曲と現在地からSpotを直接作成できるようにする。

```text
現在再生中の曲＋現在地
        ↓
Spot
```

Journeyが研究の深さを担い、Spotが参加しやすさ、比較しやすさ、公開しやすさを担う構成を目指す。

# 1. Introduction

## 1.1 背景

音楽は、人の気分や記憶だけでなく、その音楽を聴いた場所や移動体験とも結びついていると考えられる。

しかし、Spotify、Apple Music、Last.fmなどの一般的な音楽サービスでは、再生履歴は主に曲名と再生時刻の一覧として表示される。そのため、「どこを移動しながら聴いたのか」「場所が変化する中で選曲がどのように変わったのか」といった空間的・連続的な文脈は残りにくい。

一方、位置情報を利用する地図サービスやSNSでは、ユーザーが場所に関する情報を自発的に投稿したり、端末のセンサーを通じて移動情報を記録したりすることで、地理情報が蓄積されていく。このようなユーザー参加型の地理情報は、VGI（Volunteered Geographic Information）や参加型センシングの考え方と関係している。

音楽視聴履歴と位置情報を組み合わせることで、音楽を単なる時系列の再生履歴としてではなく、移動に伴って変化する時空間的な体験として扱える可能性がある。

そこで本研究では、音楽視聴履歴と連続的な位置情報を組み合わせ、移動と音楽の関係を記録・可視化・分析できる地図アプリケーション「Music Walk Map」を開発する。

## 1.2 2025年度ゼミ論

2025年度のゼミ論では、以下の機能を持つ「音楽散歩地図」のプロトタイプを開発した。

- Spotify OAuthによるユーザー認証
- Spotify APIからの再生履歴取得
- 再生中の曲の15秒間隔での監視
- Geolocation APIによる現在地取得
- OpenWeatherMap APIによる天気取得
- moodの手動登録
- Supabaseへの音楽・位置・天気情報の保存
- MapLibreによる地図上のマーカー表示
- mood、天気、時間帯による簡易集計

ゼミ論版は、個人の音楽体験を地図上で振り返ることを主な目的としていた。

[furuhashilab/2025gsc_YudaiKato](https://github.com/furuhashilab/2025gsc_YudaiKato)

ゼミ論では、再生中の曲を検出した時点の現在地を、その曲の再生場所として保存していた。

しかし、曲の再生開始時刻と位置を取得した時刻には差が生じる。また、1曲につき1地点のみを保存するため、移動中の経路、曲を聴いていた区間、前後の曲との関係を記録できなかった。

卒論版では、位置情報と音楽視聴履歴をそれぞれ独立した時系列データとして保存し、後から時刻を用いて結合する。これにより、音楽を1地点へ即座に固定するのではなく、1回の移動全体における音楽の流れとして捉える。

## 1.4 研究目的

本研究の目的は、位置情報と音楽視聴履歴を組み合わせた「Music Walk Map」を開発し、日常的な移動において、場所や移動状況の変化と音楽聴取パターンがどのように関係するかを可視化・分析することである。

また、移動全体を表すJourneyと、1曲と1地点を表すSpotを併用することで、連続的な移動体験の把握と、利用者が参加・共有しやすいデータ表現の両立を目指す。

## 1.5 リサーチクエスチョン

### 主たる問い

> 日常的な移動において、場所や移動状況の変化と音楽聴取パターンはどのように関係するのか。

### 補助的な問い

- Journeyの開始・途中・終了において、聴かれる音楽の特徴はどのように変化するか。
- 駅、公園、大学、商業地、住宅地などの場所カテゴリによって、聴かれる音楽の特徴は異なるか。
- 移動中と滞在中、または場所を通過しているときと一定時間滞在しているときでは、音楽聴取にどのような違いがあるか。
- Journeyから切り出されたSpotは、元の移動体験をどの程度表現できるか。
- その場で直接作成されたSpotと、Journeyから切り出されたSpotには、どのような違いが生じるか。
- JourneyとSpotを組み合わせることで、参加者の負担と研究データの情報量をどのように両立できるか。

# 2. Method

## 2.1 システム概要

Music Walk Mapは、音楽視聴履歴、位置情報、Journey、Spotを組み合わせたWebアプリケーションとして開発する。

想定する主要技術は以下のとおりである。

- Next.js
- React
- TypeScript
- Last.fm API
- MusicBrainz API
- Geolocation API
- Supabase
- PostgreSQL
- MapLibre GL JS
- OpenStreetMap

開発にはCodexなどのLLMを活用する。ただし、生成されたコードは技術検証、自動テスト、コードレビューを行った上で採用する。

## 2.2 データ構造の基本方針

本研究では、データを以下の3段階に分けて扱う。

| 概念 | 役割 |
| --- | --- |
| Recording Session | 位置情報と音楽履歴を収集する単位 |
| Journey | 1回の移動全体を表す研究・可視化単位 |
| Spot | 1曲と1地点を表す比較・共有単位 |

Recording Sessionでは、位置ログと音楽視聴履歴を非公開の時系列データとして収集する。

Journeyでは、Recording Sessionから得られた移動経路、曲の再生順序、曲ごとの推定区間をまとめ、1回の移動体験として扱う。

Spotでは、Journey内の1曲と代表地点を切り出すか、現在再生中の曲と現在地から直接作成する。

この構造により、Journeyの連続性を保持しながら、Spot単位での比較・集計・共有も可能にする。

## 2.3 音楽データの取得

卒論版では、音楽視聴履歴の主要な取得元としてLast.fmを利用する。

SpotifyやApple Musicなどで再生された音楽をLast.fmへScrobbleし、Last.fm APIの `user.getRecentTracks` を通じて視聴履歴を取得する。

Last.fmから取得されるデータは、次の2種類に分けて扱う。

- `nowplaying=true`を持つ再生中の曲
- 再生開始時刻を持つ確定Scrobble

再生中の曲は、Spotをその場で直接作成する際の候補表示に使用する。

Recording Session、Journey、研究用データには、再生開始時刻が確定したScrobbleを使用する。

MusicBrainzは、曲の識別情報、楽曲時間、タグなどのメタデータを補完するために利用する予定である。

## 2.4 Recording Session

Recording Sessionは、Journeyの元となる生データを収集する単位である。

想定する処理は以下のとおりである。

1. ユーザーが記録を開始する。
2. Geolocation APIを利用して位置情報を継続的に取得する。
3. 記録中の時刻、緯度・経度、測位精度などを位置サンプルとして保存する。
4. ユーザーが記録を終了する。
5. セッション時間帯に対応するLast.fmの確定Scrobbleを取得する。
6. 位置ログとScrobbleを時刻によって結合する。

位置情報と音楽履歴は、取得時点では独立して保存する。

## 2.5 Journey

Journeyは、1回のRecording Sessionで得られた移動経路と複数の曲を、一連の音楽体験として表す研究・可視化の基本単位である。

Journeyには、以下の情報を含める予定である。

- セッションの開始・終了時刻
- 移動経路
- 位置サンプル
- 聴いた曲の一覧
- 曲の再生順序
- 各曲の推定再生区間
- 各曲に対応する代表地点
- 移動距離
- 記録時間
- 場所カテゴリの変化
- 必要に応じて移動状態や滞在区間

Journeyを利用することで、1曲を1地点に単純化するだけでなく、場所の変化と音楽の変化を連続的に観察できる。

Journeyは研究上の基本単位とするが、正確な経路を常に公開するとは限らない。非公開の研究用Journey、本人だけが閲覧できるJourney、公開範囲を調整したJourneyを分けて扱う予定である。

## 2.6 Spot

Spotは、1曲と1地点を組み合わせた比較・共有単位である。

Spotの主な役割は以下の3点である。

1. Journeyを記録しない利用者でも手軽に参加できる投稿単位
2. Journey内の楽曲を曲単位で比較・集計する分析単位
3. 非公開の経路や位置ログから、公開可能な情報だけを切り出す共有単位

Spotは地図上では1つのピンとして表示する予定である。

Spotには、以下の2つの作成方法を用意する。

### 2.6.1 その場で作成

ユーザーが現在聴いている曲と現在地から、Journeyを記録せずにSpotを作成する。

想定する処理は以下のとおりである。

1. Last.fmから現在再生中の曲を取得する。
2. 投稿操作を行った時点の現在地を取得する。
3. ユーザーが曲と公開場所を確認する。
4. Spotとして地図上へ投稿する。

この方法で記録されるのは、曲の再生開始地点ではなく、ユーザーが「今ここでこの曲を共有したい」と判断した時点の場所である。

このSpotは、VGIにおける能動的な情報提供に近い。

### 2.6.2 Journeyから作成

Journey内の曲から、1曲と代表地点を選び、Spotとして切り出す。

想定する処理は以下のとおりである。

1. Recording SessionからJourneyを生成する。
2. Journey内の曲ごとに代表地点の候補を生成する。
3. ユーザーが公開する曲を選ぶ。
4. 正確な位置と公開位置を確認・調整する。
5. Spotとして地図上へ投稿する。

Journey内で聴いたすべての曲を自動公開するのではなく、ユーザーが選択した曲だけをSpotとして公開する。

内部データでは、Spotの作成方法を区別する属性を保持する予定である。

```text
instant
journey
```

## 2.7 時系列結合アルゴリズム

Last.fmの確定Scrobbleが持つ再生開始時刻を、曲区間の開始時刻として利用する。

曲の終了時刻は、以下を組み合わせて推定する。

- 次の曲の再生開始時刻
- MusicBrainzなどから得られる楽曲時間
- 楽曲時間が取得できない場合の暫定時間

曲区間内に複数の位置サンプルが存在する場合は、区間の中間時刻に最も近い位置サンプルを代表地点として選択する。

位置サンプルは緯度・経度の平均値ではなく、実際に取得された座標を使用する。

曲区間は、開始時刻を含み、終了時刻を含まない半開区間として扱う予定である。

```text
[startedAt, estimatedEndedAt)
```

結合結果は、位置データの状態に応じて以下に分類する。

| 状態 | 内容 |
| --- | --- |
| `matched` | 曲区間内に位置サンプルが存在する |
| `partial` | 曲区間外だが、許容時間内に位置サンプルが存在する |
| `unmatched` | 対応可能な位置サンプルが存在しない |
| `pending` | Last.fmの確定Scrobbleを待っている |

この結合結果は、Journey内の曲区間表示とSpot候補生成の両方に利用する。

## 2.8 場所・移動状況の付与

位置ログには、OpenStreetMapなどの地理データを用いて場所カテゴリを付与する予定である。

想定するカテゴリは以下のとおりである。

- 駅・公共交通施設
- 大学・学校
- 公園・緑地
- 商業地
- 住宅地
- 道路・歩道
- その他の公共空間

また、位置サンプルの時刻、距離、速度などから、以下のような移動状況の分類も検討する。

- 移動中
- 一時停止
- 一定時間の滞在
- Journeyの開始付近
- Journeyの途中
- Journeyの終了付近

場所カテゴリや移動状況の判定方法は、技術検証と収集データを踏まえて確定する。

## 2.9 分析方法

Journey単位とSpot単位の2段階で分析を行う予定である。

### 2.9.1 Journey単位の分析

Journeyでは、移動の連続性を保持したまま、以下を分析する。

- Journeyの開始・途中・終了における音楽の変化
- 場所カテゴリが切り替わる前後での音楽タグの変化
- 移動中と滞在中の音楽の違い
- 曲の切り替わりと場所・移動状態の切り替わりの関係
- Journeyの時間、距離、曲数の違い
- 同じユーザーにおけるJourney間の違い
- ユーザー間のJourneyの違い

### 2.9.2 Spot単位の分析

Spotでは、1曲と1地点という共通形式を用いて、以下を比較する。

- 場所カテゴリごとの曲数
- アーティスト
- 音楽タグ・ジャンル
- 再生時間帯
- Spotの作成方法（`instant` / `journey`）
- その場で作成されたSpotとJourneyから作成されたSpotの違い

Spot単位の分析は比較・集計に適している一方で、元の移動の連続性を失う。そのため、Journey単位の分析と組み合わせて解釈する。

## 2.10 データベース設計

Supabase上では、音楽、位置、Journey、Spotを単一テーブルにまとめず、役割ごとに分離する。

Migration（`supabase/migrations/20260926000000_initial_schema.sql`）として実装済みのテーブルは以下のとおりである。

- `profiles`
- `music_accounts`
- `tracks`
- `track_external_ids`
- `recording_sessions`
- `location_samples`
- `listening_events`
- `journeys`
- `join_results`
- `research_consents`

Spot関連（`spots`、`spot_tracks`、`spot_exact_locations`、`spot_locations`、`places`）と`likes`、`track_tags`は、Spot実装に合わせて後続のMigrationで追加する予定である。

Last.fmの同一Scrobbleを重複保存しないため、`listening_events.external_event_key`として、ユーザーID、音楽サービス、再生開始時刻（UNIX秒）、アーティスト名、曲名の正規化JSON配列からハッシュ生成した安定した外部イベントキーを実装した。

## 2.11 プライバシー

位置情報や移動経路は、個人の生活圏や行動を推測できる情報である。

特にJourneyは、Spotよりも情報量が多く、自宅、大学、勤務先、日常的な移動経路などを推測される危険が高い。

そのため、以下の方針を採用する予定である。

- 正確な位置ログと経路は非公開データとして保存する。
- Journeyは初期状態では非公開または本人限定とする。
- Journeyを公開する場合は、開始地点・終了地点の削除や経路の単純化を検討する。
- Spot公開時には、座標をぼかす、または「〇〇駅付近」などの場所表現へ変換する。
- Journeyからすべての曲を自動公開せず、ユーザーが選択した曲だけをSpotとして公開する。
- ユーザーが公開前に曲、場所、経路、公開範囲を確認できるようにする。
- SupabaseのRow Level Securityを利用し、ユーザーが自身の非公開データのみを操作できるようにする。
- 研究利用を行う場合は、研究同意、保存期間、利用範囲、削除方法を明示する。

| Spot（Journeyから作成） | 中核ロジック検証中 | 曲ごとの代表地点候補を生成可能、DBテーブルは未実装 |
| Last.fmアカウント連携の保存 | 未実装 | `music_accounts`テーブルは存在するが、保存処理は未実装 |
| 複数ユーザーでの共有 | 未実装 | JourneyとSpotの公開範囲を含めて設計予定 |

## 3.2 Last.fm取得検証

検証用ページ `/dev/lastfm-test` を実装した。

このページでは、Last.fm APIを15秒間隔で取得し、以下を記録できる。

- API取得時刻
- 現在再生中の曲
- 確定Scrobble
- 再生開始時刻
- ページの表示状態
- APIエラー
- JSON・CSV形式の検証ログ

通常再生、短時間でのスキップ、一定時間再生後のスキップ、同じ曲の連続再生、一時停止と再開について検証を行い、Last.fmを卒論版の音楽履歴取得元として利用できる見通しを得た。

## 3.3 位置情報取得検証

検証用ページ `/dev/location-test` を実装した。

このページでは、Geolocation APIの `watchPosition()` を利用し、以下を記録できる。

- 緯度・経度
- 測位時刻
- GPS精度
- 速度
- 方角
- 高度
- 取得間隔
- ページの表示状態
- JSON・CSV形式のログ

ただし、スマートフォンからLAN内のHTTP開発サーバへアクセスした場合、ブラウザのセキュリティ制約によって位置情報を取得できなかった。

Cloudflare TunnelによるHTTPS化も試みたが、ネットワーク環境に依存する問題が発生したため、スマートフォン実機での継続取得検証は一時保留している。

## 3.4 時系列結合検証

検証用ページ `/dev/timeline-join-test` を実装した。

実際のGPSログを待たずに、ダミー位置ログとLast.fmの確定Scrobbleを時刻で結合する純粋関数を作成した。

```ts
joinScrobblesWithLocations(
  scrobbles,
  locationSamples,
  config,
)
```

結合ロジックはReactやブラウザAPIから分離されており、将来、入力を実際のGPSログやSupabaseのデータへ差し替えられる。

現在までに以下のケースを検証している。

- 正常に曲と位置が結合できるケース
- 曲区間内の位置が不足するケース
- 対応する位置が存在しないケース
- 同じ曲を連続再生するケース
- 入力データの順番が乱れているケース
- 曲の長さが不明なケース
- 曲間に長い空白があるケース
- UTC上で日付をまたぐケース

このロジックは、当初は曲ごとのSpot候補を生成する目的で検証したが、Journey内で曲の時間的・空間的な区間を表現する基盤としても利用できる。

構想発表時点で残っていた以下の3点も修正済みである。

- 曲区間を半開区間 `[startedAt, estimatedEndedAt)` とし、境界時刻にある位置サンプルの二重所属を防止した。
- Last.fmの同一Scrobbleを再取得後も識別できる、安定した外部イベントキー（`user_id`・`provider`・`unix時刻`・アーティスト名・曲名から生成）を実装した（`src/lib/timeline-join/lastfm-external-event-key.ts`）。
- 不正な時刻・座標・曲時間・同一開始時刻などを弾く入力検証を追加した（`src/lib/timeline-join/validation.ts`）。

## 3.5 Supabaseによる永続化・認証

Supabaseプロジェクトを作成し、以下を実装した。

- `supabase/migrations/20260926000000_initial_schema.sql`：`profiles`、`music_accounts`、`tracks`、`track_external_ids`、`recording_sessions`、`location_samples`、`listening_events`、`journeys`、`join_results`、`research_consents`の10テーブルと、全テーブルへのRow Level Security（本人のみアクセス可能）を定義するMigration。
- `/auth`：Supabase Authによるメールアドレス・パスワードでのサインアップ／サインイン、確認メール経由のコールバック処理（`src/app/auth/callback/route.ts`）。
- Recording SessionとJourneyの作成・取得・一覧を行うAPIルート（`src/app/api/recording-sessions`、`src/app/api/journeys`）と、対応するDBアクセス関数（`src/lib/recording-sessions`、`src/lib/journeys`）。

現時点では、位置ログ（`location_samples`）や視聴イベント（`listening_events`）の書き込みAPI、時系列結合結果（`join_results`）の生成・保存、Last.fmアカウント連携（`music_accounts`）の保存は未実装であり、Spot関連のテーブルもMigrationにまだ含めていない。

# 4. Discussion

## 4.1 Journeyを研究の中心とする理由

Spotは1曲と1地点を組み合わせるため、場所カテゴリごとの比較や地図上での共有に適している。

一方、実際の音楽体験では、1曲を聴いている間にも利用者は移動し、場所が変化する場合がある。曲を代表地点1つに結びつけると、以下の情報が失われる。

- どこからどこへ移動していたか
- 曲の途中で場所がどのように変化したか
- 前後にどの曲を聴いていたか
- 移動中か滞在中か
- 場所の切り替わりと曲の切り替わりの関係

Journeyでは、位置と音楽の連続性を保持することで、音楽を伴う移動体験を時空間的なデータとして扱える。

そのため本研究では、Journeyを研究・可視化の中心とし、SpotをJourneyから切り出せる比較・共有単位として位置付ける。

## 4.2 Spotの存在意義

SpotはJourneyより情報量が少ないが、単なる簡略版ではない。

Spotには、主に以下の意義がある。

### 1. 参加しやすさ

Journeyでは、記録開始、移動、記録終了、内容確認という操作が必要になる。

Spotをその場で直接作成できれば、長時間の位置記録を行いたくない利用者や、移動ではなく特定の場所で音楽を聴いている利用者も参加できる。

### 2. 比較しやすさ

Journeyは時間、距離、曲数が異なるため、そのまま単純比較することが難しい。

Journey内の楽曲をSpotとして切り出すことで、共通の「1曲＋1地点」という形式で場所カテゴリ別の比較や集計ができる。

### 3. 公開しやすさ

Journeyの経路全体には、自宅、大学、勤務先などを推測できる情報が含まれる可能性がある。

非公開のJourneyから、ユーザーが選んだ曲とぼかした代表地点だけをSpotとして公開することで、移動履歴全体を公開せずに音楽体験を共有できる。

つまり、Journeyが研究の深さを担い、Spotが参加しやすさ、比較しやすさ、公開しやすさを担う。

## 4.3 現時点で得られたこと

Last.fmの確定Scrobbleが持つ再生開始時刻と、独立して記録した位置情報を時刻で結合する方式は、Journeyを生成するための基礎として利用できる見通しが得られた。

ゼミ論版では、再生中の曲を検出した時点で現在地を1回取得していた。そのため、再生開始地点ではなく、検出時点の位置が保存される可能性があった。

卒論版では、音楽と位置を独立した時系列として保持することで、曲が再生されていた区間と、その間の位置変化を後から扱える。

また、結合結果へ `matched`、`partial`、`unmatched`などの状態を残すことで、研究分析時に信頼度の低いデータを識別できる。

## 4.4 現在の課題

現在の主な課題は以下のとおりである。

- スマートフォンのHTTPS環境で連続位置取得を検証できていない。
- モバイルブラウザのバックグラウンド時や画面ロック時の挙動が未確認である。
- Journeyの開始・終了を利用者の操作に任せるか、自動判定を取り入れるか検討が必要である。
- 徒歩、電車、自転車などの移動手段を区別するか決める必要がある。
- 滞在と通過をどのように判定するか検討が必要である。
- MusicBrainzから楽曲時間やタグを安定して取得できるか検証が必要である。
- Recording Sessionで取得した位置ログ・視聴イベントをDBへ書き込むAPIが未実装である。
- 時系列結合処理（`joinScrobblesWithLocations`）とJourney生成をサーバー上で連携させる処理が未実装である。
- Last.fmアカウント連携情報（`music_accounts`）の保存処理が未実装である。
- Spot関連テーブルとAPIが未実装であり、正確な経路・位置と公開情報を分離する仕組みも未実装である。
- Journey同士を比較する分析指標を具体化する必要がある。
- 研究で収集するJourney数、参加者数、期間、同意方法を確定する必要がある。
- Journeyを記録する参加者の操作負担を評価する必要がある。

## 4.5 研究上の限界とリスク

Journey中心の研究はSpot中心の研究よりも情報量が多く、移動と音楽の関係を深く扱える可能性がある。

一方で、以下のリスクがある。

- 位置情報の連続取得がモバイルブラウザ上で安定しない可能性
- バッテリー消費や操作負担によって参加者が継続利用しない可能性
- Journeyごとの長さや曲数が異なり、比較方法が複雑になる可能性
- 十分なJourney数を収集できない可能性
- 正確な経路を扱うことによるプライバシー上のリスク

そのため、研究の中心はJourneyとしながらも、Spotによる簡易参加と曲単位の分析を最低保証ラインとして残す。

# 5. Conclusion

## 5.1 最終ゴール

卒業論文の最終ゴールは、以下の3点である。

### 1. Journeyを記録・可視化できるプロトタイプの開発

最低限、以下の機能を持つWebアプリケーションを完成させる。

- ユーザー認証
- Last.fmアカウント連携
- Recording Sessionの開始・終了
- 位置ログの保存
- Last.fm Scrobbleの取得
- 位置ログとScrobbleの時刻結合
- Journeyの生成
- 移動経路と曲順の地図表示
- Journeyの開始・途中・終了の確認
- Journeyの公開範囲設定
- 正確な経路と公開用情報の分離

### 2. Spotによる参加・比較・共有機能の実装

最低限、以下のSpot機能を実装する。

- 現在再生中の曲と現在地からSpotを作成
- Journey内の曲からSpot候補を生成
- ユーザーによる曲と場所の確認
- 公開位置のぼかし
- 地図上でのSpot表示
- 他ユーザーの公開Spotの閲覧
- Spotの作成方法の記録

いいね、コメント、フォローなどの一般的なSNS機能は、研究上の必要性と開発状況を踏まえて優先度を判断する。

### 3. 移動と音楽の関係の分析

収集したJourneyとSpotを用いて、以下を分析する。

- 場所カテゴリの変化と音楽の変化
- Journeyの開始・途中・終了における音楽の特徴
- 移動中と滞在中の違い
- Spot単位の場所カテゴリ別比較
- その場で作成されたSpotとJourneyから作成されたSpotの違い
- JourneyからSpotへ単純化することで失われる情報

## 5.2 最低保証ライン

Journey中心の研究は、位置情報の連続取得やデータ収集に失敗するリスクがある。

そのため、卒論としての最低保証ラインを以下のように設定する。

1. Last.fmの確定Scrobbleを取得できる。
2. 位置ログとScrobbleを時刻で結合できる。
3. 記録セッションをJourneyとして保存・可視化できる。
4. Journey内の曲からSpotを生成できる。
5. Spot単位で場所カテゴリ別の比較ができる。

Journeyの高度な共有機能、移動手段の自動判定、いいね・コメントなどは必須条件に含めない。
