# Last.fm 視聴履歴検証手順

## 準備

必要な環境変数を `.env.local` に設定する。

```env
LASTFM_API_KEY=Last.fmで発行したAPIキー
LASTFM_USERNAME=検証対象のLast.fmユーザー名
```

APIキーは [Last.fm API account](https://www.last.fm/api/account/create) で発行する。キーとユーザー名はサーバー側だけで利用し、APIレスポンスやブラウザーのログには含めない。

```bash
pnpm install
pnpm dev
```

検証ページは `http://localhost:3000/dev/lastfm-test`。表示直後から15秒間隔で取得し、画面をバックグラウンドにした場合も各レスポンス受信時の `document.visibilityState` を記録する。ブラウザーはバックグラウンドタブのタイマーを間引く場合があるため、取得間隔そのものも結果として記録する。

## 共通して記録する結果

- プレイヤーで操作した実時刻（秒まで）
- `nowplaying=true` を初めて観測したAPI取得時刻と、その遅延
- nowplayingが消え、同じ曲が確定Scrobbleとして現れたAPI取得時刻と、その遅延
- 確定履歴の `playedAt` / `playedAtUnix`（Last.fmが返す再生開始時刻）
- スキップ曲が確定履歴に残ったか
- 同一曲の連続再生が別のUnix秒を持つ複数行になったか
- 一時停止中と再開後のnowplaying、確定履歴の変化
- APIエラー、visibilityState、15秒から大きく外れた取得間隔

操作時刻は別途メモし、検証終了後に画面からJSONとCSVの両方を保存する。CSVはUTF-8 BOM、CRLF、全セルを引用符で囲む形式で、ExcelとGoogle Sheetsへの取り込みを想定している。

## テストA：1曲を通常再生

1. ログをクリアし、停止状態から曲を再生する。
2. 曲を最後まで再生し、次の曲へ移るまで待つ。
3. nowplayingの初回検出、確定への移行、再生開始時刻を記録する。

合格条件：再生中と確定履歴が区別され、確定後の `playedAtUnix` が操作時刻と整合し、ポーリングログからそれぞれの遅延を算出できる。

## テストB：30秒程度でスキップ

1. 曲を再生して約30秒で次の曲へスキップする。
2. 数回分のポーリング後、スキップ曲が確定履歴に現れるか確認する。

合格条件：スキップ曲が残るか否かをログで明確に判定でき、次の曲のnowplayingと混同されない。

## テストC：半分以上聴いてスキップ

1. 曲の総時間を記録し、半分以上再生してからスキップする。
2. 確定履歴への追加時刻と再生開始時刻を確認する。

合格条件：Scrobble確定の有無と確定までの遅延をテストBと比較できる。

## テストD：同じ曲を連続再生

1. 同じ曲を2回連続で、Scrobble条件を満たすまで再生する。
2. 確定履歴に同じ曲名・アーティストの行が2件現れるか確認する。

合格条件：2件がそれぞれ異なる `playedAtUnix` を持ち、別履歴として保存ログに残る。

## テストE：一時停止・再開

1. 再生中に一時停止し、停止時刻と停止時間を記録する。
2. 1分以上待ってから再開し、曲をScrobble条件まで再生する。
3. 一時停止中、再開直後、確定後の各ログを比較する。

合格条件：一時停止・再開によるnowplayingの変化、確定タイミング、`playedAtUnix` の扱いを時系列で説明できる。

## 全体の合格条件

- すべてのテストで15秒ごとの取得結果がブラウザーメモリに最新順で残る。
- 再生中は `nowPlaying=true` かつ再生開始時刻なし、確定履歴は `nowPlaying=false` かつ有効な再生開始時刻として区別される。
- JSON/CSVを保存し、API取得時刻・可視状態・曲・状態・再生開始時刻を後から分析できる。
- API障害や設定不足が画面上のエラーとして確認でき、既存機能やDBへ書き込まない。
